# smart-app-store-review

Audits an Apple-platform app against the App Store Review Guidelines, cleans up
what would get it rejected, and verifies it is likely to pass. Rule content is
adapted from [safaiyeh/app-store-review-skill](https://github.com/safaiyeh/app-store-review-skill)
(MIT) and is current through Apple's **October 16, 2026** guidelines update.

## Brain Protocol (read BEFORE creating anything)

1. `references/_index.md`       - what this skill knows (map)
2. `references/patterns.md`     - what worked, with numbers
3. `references/decisions.md`    - past reasoning, don't repeat mistakes
4. `references/log.md`          - last 5 session entries
5. Relevant `references/wiki/<context>/<category>/` concepts per task

After completing work, UPDATE the brain:
- New user-provided material lives in `references/raw/` (LLM never renames or edits it)
- Distilled insights -> new/updated `references/wiki/<context>/<category>/<concept>.md`
  - Cite every raw file you used in the `sources:` frontmatter array

- Non-obvious decisions -> `decisions.md`
- Session summary (always) -> append to `log.md`
- Run `scripts/lint.sh` to regenerate `_index.md` and verify structure

Every 2 weeks OR when requested: run `scripts/lint.sh` for contradictions,
stale data, orphan wiki pages, orphan raw files, and broken `sources:` paths.

No data, no improvement.

## When to Use

- Before the first App Store submission, or before an update ships
- After a rejection: start at the guideline number in Apple's message
- When building payments, accounts, UGC or AI generation, ads or tracking, kids features
- "Clean up" a repo for release: logs with secrets, placeholder copy, Android mentions, pre-checked terms

## How to Use

**Live map of concepts:** `references/_index.md` (regenerated by `scripts/lint.sh`).

**Run a review (always start here):**
Read `references/wiki/review/workflow/audit-loop.md`: scope, `scripts/scan.sh`, verify, clean up, report.

**Turn scanner candidates into findings without false rejections:**
Read `references/wiki/review/workflow/evidence-gate.md`.

**Decide what to fix and what to only report:**
Read `references/wiki/review/cleanup/safe-fixes.md`.

**Look up a guideline number or topic (full rules, Swift and RN/Expo examples):**
Read `references/wiki/review/guidelines/section-map.md`, then only the matching
section of `references/raw/upstream/<n>-<section>.md`.

**Final gate, including App Store Connect items code cannot prove:**
Read `references/wiki/review/submission/pre-submission-checklist.md`.

**Write the report:** `references/wiki/review/report/findings-format.md`.

### Scripts

- `scripts/scan.sh [repo]` - prints candidates as `SEVERITY  GUIDELINE  file:line  check-id  text`. Lists only; never a verdict.
- `scripts/lint.sh` - brain health check.
- `tests/run.sh` - hermetic fixture test for scan.sh (`/bin/bash tests/run.sh`).

## Hard rules

- A candidate becomes a finding only with the evidence named in the evidence gate. Otherwise say NEEDS-VERIFICATION and what to check.
- Establish storefront and platform before flagging any external purchase link.
- Cleanup edits need one confirmation of the full list. Never edit payments, auth, account deletion, ATT logic, or purpose-string wording on your own.
- Cite a guideline number on every finding. Checks the upstream reference does not cover are labeled `beyond-reference` with the App Store Connect error code.
- If today is more than ~3 months past the currency date above, check Apple's developer news for guideline changes and state the date reviewed against.

## Examples

### Example 1: pre-submission audit of an Expo app

User says: "Will this pass App Store review? We submit Friday."

Actions:
1. Scope: Expo managed, iOS + iPad, US + EU, accounts, RevenueCat subscriptions, AppsFlyer
2. `bash scripts/scan.sh .` gives 14 candidates. The evidence gate confirms 3, leaves 2 to verify, drops 9 (vendored or test code)
3. With approval, fixes `secret-in-log`, `precheck-terms` and `pre-permission-wording`; reports 5.1.2 (AppsFlyer before ATT) for a decision
4. Re-scans clean, runs `npx expo-doctor` and the test suite, then gives the report and the App Store Connect checklist (demo account, Notes for Review)

Result: one table of CONFIRMED / NEEDS-VERIFICATION / FIXED rows, each with a guideline and file:line.

### Example 2: responding to a rejection

User says: "Apple rejected us under Guideline 5.1.1(v), what do we change?"

Actions:
1. Read the 5.1.1(v) section of `raw/upstream/5-legal.md`
2. Locate account creation, then check for an in-app path that initiates deletion
3. Report the gap and the minimum compliant fix (an in-app button, or a direct link to a page that completes deletion), plus the reply text for Resolution Center

Result: a targeted fix plan, with no repo-wide noise.

## Feedback

If the skill misfires (false positive, false negative, wrong citation, outdated
rule, bad fix), offer once per session to draft a GitHub issue for
`jjfantini/humblSKILLS`. Show the full draft first. Never include the user's
code, app name, bundle IDs, paths or credentials. Send only after the user
approves the exact text (`gh issue create --repo jjfantini/humblSKILLS ...`).
Never send silently. If the issue is in the upstream rule text, say so,
so it can be reported to safaiyeh/app-store-review-skill.

## Success Signals

- Every reported finding has a guideline number, file:line (or ASC item) and a concrete fix
- Zero findings rest on an import or URL alone; each one is CONFIRMED with evidence or marked NEEDS-VERIFICATION
- `scripts/scan.sh` re-run after cleanup shows the fixed candidates gone and nothing new
- `/bin/bash tests/run.sh` passes; `scripts/lint.sh` exits 0
- The report states which guidelines date it was checked against
